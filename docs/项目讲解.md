## 0. 这个项目是干什么的

**mini-dts = 一个缩微版的"数据库搬家 + 持续同步"引擎**（对标阿里云 OMS / Data Transmission Service）：

把一个 MySQL 库（源）的数据迁移到另一个 MySQL（目标），并且迁移完成后还能**持续同步**源库的新增改动，全程支持暂停/恢复/崩溃续传，最后还能做数据一致性校验。

一次任务的生命周期：

```
建任务(校验环境/主键) ──▶ 全量迁移(把存量数据分片搬过去)
   │                          │ 记录"一致性位点"(GTID)
   ▼                          ▼
 全量完成 ──▶ 增量同步(订阅源库 binlog，把全量期间的+之后的改动重放)
   │
   ├── 可随时 暂停/恢复（断点续传）
   ├── CRC 对账（比对两端每个分片的校验和）
   └── 追平后 finish（收尾）
```

整个仓库 7 个 Maven 模块（≈7 个 npm 包），约 2500 行主代码 + 约 1000 行测试：

```
                    ┌──────────────────────────────┐
                    │   mini-dts-starter (装配+API) │ ← Spring Boot 入口、编排所有模块
                    └──────────────┬───────────────┘
        ┌──────────┬───────────────┼──────────────┬─────────────┐
        ▼          ▼               ▼              ▼             ▼
   mini-dts-cm  full          store(增量)    verifier(校验)  connector(写入)
   (控制面)    (全量)         binlog解析       CRC对账        MySqlSink幂等写
        │          │               │              │             │
        └──────────┴───────┬───────┴──────────────┴─────────────┘
                           ▼
                   mini-dts-common
              (数据模型/编码/分片/端口接口)
```

**模块一句话职责**（README 的表格翻译成人话）：

| 模块 | 人话 |
|---|---|
| `common` | 大家共用的"词汇表"：一条数据长什么样（RowRecord）、怎么把一行数据编码成字符串（RowCodec）、怎么分片、几个回调接口 |
| `connector` | 往目标库写数据的"笔"：批量幂等写入，数据+位点同事务 |
| `full` | 全量搬运工：按主键把源表切片，多线程拷贝，支持断点续传 |
| `store` | 增量监听器：伪装成 MySQL 从库读 binlog，把变更翻译成 RowRecord |
| `verifier` | 质检员：对每个分片算 CRC 校验和，两边不一致再逐行比对 |
| `cm` | 管理后台：任务元数据存 H2 数据库、状态机、REST API |
| `starter` | 总装车间：Spring Boot 启动类 + 把上面所有零件拼成完整系统的 MigrationEngineImpl |

## 1. Java 速成

你只需要看懂本项目用到的语法。下面全部用 TypeScript 做对照。

### 1.1 基本形态

```java
package com.minidts.common;            // 声明"我在哪个命名空间"（= 文件所在目录的约定）
import java.util.List;                 // 引入别的类（≈ import ... from ...）

public class Foo {                     // 定义一个类；public = 对外可见
    private final String name;         // 字段；private = 仅类内可见；final = 赋值后不可变（≈ const）

    public Foo(String name) {          // 构造函数（和类同名；≈ TS constructor）
        this.name = name;              // this 和 JS 一样
    }

    public String name() { ... }       // 方法；String 是返回类型，写在方法名前面！
}
```

关键差异（最容易绊倒你的 4 点）：

1. **类型写在前面**：`List<String> cols`（Java）vs `let cols: string[]`（TS）。
2. **语句以分号结尾**，代码块用 `{}`，和 JS 一样。
3. **`void`** = 没有返回值（≈ TS 的 `: void`）。
4. **命名习惯**：类名大驼峰 `RowRecord`，方法/变量小驼峰 `writeBatch`，常量全大写 `COL_SEP`。

### 1.2 record：Java 16+ 的"纯数据对象"（本项目大量使用）

```java
public record RowRecord(String schema, String table, List<String> columns, ...) {}
```

一行顶 TS 里一大段：

```ts
// 等价的 TS 大致是：
class RowRecord {
  constructor(public schema: string, public table: string, ...) {}
  // 并且自动获得：equals、hashCode、toString、解构式构造器
}
```

- 访问字段**不带 get**：`r.table()`（record 自动生成与字段同名的方法）。
- record 有个特殊的**紧凑构造函数**，可以在创建时做加工/校验（本项目 `RowRecord` 用它做了防御性拷贝）：

```java
public record RowRecord(...) {
    public RowRecord {                       // 注意：没有括号参数列表，这是"紧凑构造函数"
        columns = List.copyOf(columns);      // 这里改写的值会成为真正的字段值
        if (columns.size() != values.size()) // 可以在这里校验、抛异常
            throw new IllegalArgumentException("...");
    }
}
```

### 1.3 enum：枚举（带方法的常量集合）

```java
public enum OpType { UPSERT, DELETE }        // ≈ enum OpType { UPSERT = ..., DELETE = ... }
```

使用：`r.op() == OpType.UPSERT`，取名字：`r.op().name()` 返回 `"UPSERT"` 字符串。

### 1.4 interface：接口（比 TS 的强）

```java
public interface Sink extends AutoCloseable {     // extends 这里是"继承接口"
    void writeBatch(List<RowRecord> batch, String gtid) throws SQLException;  // 只声明，不实现
    @Override default void close() {}             // default 方法 = 接口自带的默认实现
}
```

一个类用 `implements` 实现接口：`class MySqlSink implements Sink { ... 必须实现 writeBatch ... }`。
`@Override` 是注解（见 1.9），意思是"我重写了父类/接口的方法"，写错方法名编译器会报错。

`AutoCloseable` 是 Java 的特殊接口：实现它的对象可以放进 `try (...)` 里自动关闭（见 1.7）。

### 1.5 集合与泛型

```java
List<String> cols = new ArrayList<>();     // ArrayList = 可变数组（≈ JS array）；List 是接口
cols.add("a");                             // ≈ push
cols.get(0);                               // ≈ cols[0]，但只能用 get
cols.size();                               // ≈ length

Map<String, Long> m = new HashMap<>();     // ≈ Map / 普通对象
m.put("a", 1L);                            // ≈ set
m.get("a");                                // ≈ get（不存在返回 null，不是 undefined）
m.merge("a", 5, Math::max);                // "如果有旧值就和旧值合并，没有就放入"（很好用的原子操作）

Set<String> done = new HashSet<>();        // ≈ Set

List.of("a", "b")                          // 不可变 List（≈ Object.freeze 效果），不能 add
Map.copyOf(m)                              // 不可变 Map
```

- `1L`：Java 里整数默认是 int，加 L 表示 long（64 位）。
- `TreeMap` = 按 key 排序的 Map；`LinkedHashMap` = 保持插入顺序的 Map。

### 1.6 lambda、方法引用、函数式接口

```java
list.stream().map(c -> quote(c)).toList();      // c -> quote(c)  就是箭头函数
list.stream().map(Foo::quote).toList();         // Foo::quote 是方法引用（省掉参数名）
Math::max                                        // 也是方法引用，等价 (a, b) -> Math.max(a, b)
() -> new MySqlSink(...)                         // 无参 lambda，常见于"惰性创建"
```

只有**恰好一个抽象方法**的接口才能接 lambda，这种接口常标注 `@FunctionalInterface`，比如本项目：

```java
@FunctionalInterface
public interface SinkFactory { Sink open() throws SQLException; }
// 用法：传 () -> new MySqlSink(...)，调用 factory.open() 时才真正创建
```

（≈ TS 里 `type SinkFactory = () => Sink`。）

### 1.7 异常与 try-with-resources（本项目核心安全机制）

Java 异常分两档：

- **非受检异常**（`RuntimeException` 及其子类）：可不捕获，抛出即中断，≈ TS 的 `throw new Error()`。本项目的 `DtsException` 就是这档。
- **受检异常**（如 `SQLException`）：编译器**强制**你要么 `try/catch` 要么方法签名上写 `throws SQLException` 声明"我可能抛这个"。

```java
try (Connection c = Connections.open(ep);        // try-with-resources：小括号里声明的对象，
     Sink sink = factory.open()) {               // 在 try 结束时【自动调用 close()】，即使抛异常也关
    // 用 c 和 sink
} catch (SQLException e) {                       // ≈ catch (e)
    throw new DtsException("...", e);            // 包一层再抛（e 作为 cause 保留原始堆栈）
}
```

这套 `try (...)` 就是 Java 版的 `using` / 手写 `finally { close() }`，数据库连接全都这么管理，**没有内存泄漏的可能**。

### 1.8 字符串与常用工具

```java
String.join(",", list)               // ≈ list.join(",")
s.split(",")                          // ≈ split
s.toUpperCase() / isBlank() / trim()  // 注意 isBlank() = 空或全空白
"ab".repeat(3)                        // "ababab"
String.format("%09d", 123)            // 9 位补零 → "000000123"
new StringBuilder()                   // 可变字符串（循环拼接用，性能好）；sb.append(x)
HexFormat.of().formatHex(bytes)       // 字节数组 → 小写 hex 字符串（Java 17）
"""/** 文本块 */"""                    // 三引号多行字符串（Java 15+），本项目用它写 SQL
```

### 1.9 注解（Annotation）

`@Xxx` 不是装饰器语法糖，而是**给编译器/框架看的元数据**：

- `@Override`：我重写了父类方法（编译器校验）。
- `@FunctionalInterface`：声明这是函数式接口（编译器校验只有一个抽象方法）。
- Spring 系：`@RestController`、`@Bean`、`@Configuration`… 见 §10/§11 讲解。

### 1.10 模式匹配与 var（新语法，本项目在用）

```java
if (v instanceof Long l) return "N:" + l;   // 判断类型的同时声明变量 l（≈ TS 的类型收窄）
var rs = ps.executeQuery();                  // var = 让编译器自己推断类型（≈ TS 的 let 不写类型）
```

### 1.11 并发（本项目全用到了，重点！）

```java
// ① 最原始：开一个线程（≈ worker）
Thread t = new Thread(() -> svc.run());   // 参数是"要执行的任务"（lambda）
t.start();                                // 异步启动

// ② 线程池：固定 N 个线程反复利用
ExecutorService executor = Executors.newFixedThreadPool(4);
Future<?> f = executor.submit(() -> copyChunk(...));  // 提交任务，拿到"未来结果"的凭据
f.get();                                 // 阻塞等任务完成；任务里抛的异常会在这里重新抛出

// ③ 多线程可见性
private volatile boolean stopped = false; // volatile：一个线程改了，别的线程立刻可见（否则可能读缓存旧值）

// ④ 原子计数器（线程安全的 count++）
AtomicLong rowsCopied = new AtomicLong();
rowsCopied.incrementAndGet();             // ++rowsCopied 的线程安全版
rowsCopied.addAndGet(n);                  // += n 的线程安全版
rowsCopied.get();                         // 读值

// ⑤ 并发安全 Map
ConcurrentHashMap<String, Runtime> runtimes = new ConcurrentHashMap<>();
runtimes.put(id, rt);                     // 多线程同时读写不炸

// ⑥ 互斥锁（比 synchronized 灵活）
ReentrantLock lock = new ReentrantLock();
lock.lock();
try { ... 临界区 ... } finally { lock.unlock(); }

// ⑦ synchronized 方法：整个方法加锁，同一对象同时只有一个线程能进
public synchronized void add(String sid, long gno) { ... }
```

线程中断礼仪：收到 `InterruptedException` 时要 `Thread.currentThread().interrupt()` 恢复中断标记再退出——本项目 TokenBucket 就是这么写的。

## 3. 数据库前置知识

### 3.1 JDBC：Java 操作数据库的标准 API

不管连 MySQL 还是别的库，代码都长这样（先混个脸熟，后面逐行讲）：

```java
Connection conn = DriverManager.getConnection(url, user, password);  // 建立连接
PreparedStatement ps = conn.prepareStatement("SELECT * FROM t WHERE id = ?");  // ? 是占位符
ps.setObject(1, 42);                 // 给第 1 个 ? 填值（从 1 开始数，不是 0！）
ResultSet rs = ps.executeQuery();    // 执行查询，返回"游标"
while (rs.next()) {                  // next() 把游标往后挪一行，没有下一行返回 false
    Object v = rs.getObject(1);      // 取当前行第 1 列
}
ps.executeUpdate();                  // 执行 INSERT/UPDATE/DELETE，返回影响行数
```

要点：
- **PreparedStatement + `?` 占位符** = 防注入 + 预编译，等价于你习惯的参数化查询。本项目所有 SQL 都这样拼。
- **事务**：连接默认 `autoCommit=true`（每条 SQL 自动提交）。手动事务的标准写法：

```java
boolean old = conn.getAutoCommit();
conn.setAutoCommit(false);           // 开启手动事务
try {
    ...写数据...
    conn.commit();                   // 全部成功才提交
} catch (Exception e) {
    conn.rollback();                 // 任何一步炸了，全部回滚
    throw e;
} finally {
    conn.setAutoCommit(old);         // 恢复现场
}
```

- **INFORMATION_SCHEMA**：MySQL 自带的"记录元数据的数据库"（有哪些表/列/主键都存这里），本项目靠它解析主键和列。

### 3.2 H2：测试用的"假 MySQL"

H2 是一个纯 Java 写的嵌入式数据库，可以设 `MODE=MySQL` 模拟 MySQL 方言。单测里用两个 H2 库分别扮演"源库/目标库"，**不需要 Docker、不需要真 MySQL**，跑得飞快。所以你会看到 `isMysql ? A写法 : B写法` 这种分支——生产走 MySQL 分支，测试走 H2 分支。

### 3.3 binlog：MySQL 的"操作录像"

MySQL 每次改数据，都会往 binlog（二进制日志）里按顺序记一笔。从库同步、数据订阅都靠读它。本项目用到的关键点：

- **binlog_format=ROW**：记录"改之后的整行数据"（而不是 SQL 语句），才能忠实回放。
- **binlog_row_image=FULL**：UPDATE/DELETE 也要记录**改之前**的完整行（前镜像），主键变更检测靠它。
- **GTID**：每个事务的全局唯一编号，格式 `3E11FA47-71CA-11E1-9E33-C80AA9429562:23`（`服务器UUID:事务序号`）。有了它，"我同步到哪了"只需存一个编号集合，断点续传就是"从编号 X 继续读"。`gtid_executed` 变量 = 这个库已经执行过的事务集合。
- **伪装从库**：第三方库 `mysql-binlog-connector-java` 让 Java 程序像 MySQL 从库一样连上主库拉 binlog 流，逐事件回调。
- **binlog 事件类型**（store 模块会逐个处理）：`TABLE_MAP`（接下来要出现的表编号→表名）、`GTID`（一个事务开始）、`WRITE_ROWS/UPDATE_ROWS/DELETE_ROWS`（行变更）、`XID`（一个事务提交）。

### 3.4 迁移领域的几个术语

- **全量（full）**：把存量数据搬过去；**增量（incr/incremental）**：持续同步新改动。
- **分片（chunk/shard）**：把大表按主键切成小段，一段一段搬。好处：内存可控、可并行、可断点。
- **键集分页（keyset pagination）**：用 `WHERE pk > 上一个边界 ORDER BY pk` 翻页，而不是 `LIMIT 10000 OFFSET 5000000`（后者要扫过前 500 万行，深翻页越翻越慢）。
- **幂等（idempotent）**：同一条数据写一遍和写三遍结果相同。MySQL 的 `INSERT ... ON DUPLICATE KEY UPDATE`（存在则更新，不存在则插入，即 **upsert**）是本项目幂等的基石。
- **至少一次（at-least-once）**：可能重复投递但不丢；**恰好一次（exactly-once）**：不重不丢。业界通行做法 = 至少一次 + 幂等消费 = 效果上的恰好一次，本项目正是这么做的。
- **CRC32**：对一个字符串算 32 位校验和，内容稍有不同结果就大变。比对两库数据一致性的低成本手段：先比分片 CRC（快），不一致再逐行比（慢但精确）。
- **令牌桶（token bucket）**：限速算法。桶里最多 N 个令牌，每秒补充 N 个；每搬一行要消耗 1 个令牌，桶空了就等着——保护源库不被拉爆。
- **死信（dead letter）**：处理失败的消息单独存一张表留底，不让一条毒数据卡死整个任务。

### 5.9 `RowCodec.java`（90 行）★红线 R1：行编码器

**解决什么**：校验时要比"源库这行"和"目标库这行"是否完全一致。但两边的驱动、时区、浮点表示可能略有差别。所以定义一套**严格到偏执的编码规则**，两边都编码成字符串后比较——规则里任何一点松动都会造成"数据明明一样、CRC 却不同"的假报错。

编码规则（类注释原文翻译）：
- 列按建表顺序（ORDINAL_POSITION）排列；
- 每列 = `类型标签 + ':' + 值`，列之间用 `\u0001`（不可见控制字符 SOH）分隔；
- NULL 用哨兵串 `\u0002NULL`；
- 数值一律 `BigDecimal.toPlainString()`（**禁止科学计数法**：`1E-9` 必须输出 `0.000000001`）；
- 时间固定补齐到 9 位纳秒（`12:30:00.123000000`）；
- 二进制转小写 hex。

```java
public static final String COL_SEP = "\u0001";
public static final String NULL_SENTINEL = "\u0002NULL";
// static final = 类级常量（≈ 模块级 const）。选控制字符做分隔符：数据里不可能出现，天然免转义

private static final DateTimeFormatter TS = DateTimeFormatter.ofPattern("yyyy-MM-dd'T'HH:mm:ss.SSSSSSSSS");

private RowCodec() {}                    // 又一个纯静态工具类

public static String encode(List<String> columns, List<Object> rawValues) {
    if (columns.size() != rawValues.size()) { ... throw ... }   // 契约校验
    StringBuilder sb = new StringBuilder(Math.max(32, columns.size() * 16));
    // StringBuilder：可变字符串。循环拼接别用 s += （每次都新建对象），用这个（≈ JS 的数组 push 后 join）

    for (int i = 0; i < rawValues.size(); i++) {
        if (i > 0) sb.append(COL_SEP);   // 列间加分隔符（第一列前不加）
        sb.append(cell(Values.normalize(rawValues.get(i))));
        // 每个值：先归一化（§5.8）再编码成"标签:值"
    }
    return sb.toString();
}

public static String encode(RowRecord r) { return encode(r.columns(), r.values()); }
// 便捷重载：直接吃 RowRecord。Java 支持"同名方法不同参数"（方法重载 overload）
```

`cell`——单个值 → `标签:值` 字符串（模式匹配语法高发区）：

```java
public static String cell(Object v) {
    if (v == null) return NULL_SENTINEL;               // null → \u0002NULL
    if (v instanceof Long l) return "N:" + l;          // 数字：N:
    if (v instanceof Boolean b) return "N:" + (b ? 1 : 0);   // 布尔也归到数字：true=1
    if (v instanceof BigDecimal bd) return "N:" + bd.toPlainString();
    // toPlainString：1E-9 → 0.000000001。这是"禁止科学计数法"的落实点
    if (v instanceof String s) return "S:" + s;        // 字符串：S:
    if (v instanceof byte[] bytes) return "B:" + HexFormat.of().formatHex(bytes);
    // 二进制：B: + 小写hex（Java 17 的 HexFormat）
    if (v instanceof LocalDateTime dt) return "D:" + padNanos(dt);   // 时间：D:
    if (v instanceof LocalDate d) return "D:" + d.toString();
    if (v instanceof LocalTime t) return "D:" + padNanosTime(t);
    throw new IllegalStateException("unencodable value type: " + ...);
    // 不认识就炸——比静默输出错误格式强一万倍
}
```

纳秒补齐的两个私有方法：

```java
private static String padNanos(LocalDateTime dt) {
    return dt.format(DateTimeFormatter.ofPattern("yyyy-MM-dd'T'HH:mm:ss"))
            + String.format(".%09d", dt.getNano());
    // 秒部分正常格式化，纳秒部分用 %09d 补足 9 位。
    // 为什么必须补齐：MySQL datetime(0) 读出来可能是 "12:30:00"（无小数），datetime(3) 是 "12:30:00.123"，
    // 直接 toString 两边格式不同就假不一致；统一补成 9 位后只比内容

```

```java
public static long crc32(String s) {

    crc.update(s.getBytes(StandardCharsets.UTF_8));     // 字符串 → UTF-8 字节 → 喂给 CRC
```

### 5.11 `GtidState.java`（55 行）——GTID 集合

**解决什么**：维护"我已经回放到哪些事务了"。简化模型：每个源服务器（sid）记一个最大事务号（gno），序列化成 `"sidA:1-100,sidB:1-5"` 这样的集合字符串——正是 MySQL `gtid_set` 的格式，可以直接喂给 binlog 客户端做续传起点。

```java
private final TreeMap<String, Long> maxGno = new TreeMap<>();
// TreeMap：按 key 排序的 Map → 序列化出来的字符串顺序稳定（测试好写，比较好比）

public static GtidState of(String gtidSet) {
    // 解析："sid:1-100,sid:1-200" → {sid: 200}
    GtidState s = new GtidState();
    if (gtidSet == null || gtidSet.isBlank()) return s;
    for (String part : gtidSet.split(",")) {           // 按逗号切开每段
        part = part.trim();                            // 去两端空白
        if (part.isEmpty()) continue;                  // continue = 跳过本轮循环（JS 同款）
        String[] segs = part.split(":");               // "sid:1-100" → ["sid", "1-100"]
        if (segs.length < 2) continue;
        String sid = segs[0];
        String[] ranges = segs[1].split("-");          // "1-100" → ["1","100"]
        long max = Long.parseLong(ranges[ranges.length - 1]);
        // 只取区间右端（最大值）——这就是"max-per-sid"简化
        s.maxGno.merge(sid, max, Math::max);
        // merge 的语义：key 不存在 → 放入 max；存在 → 用 Math::max(旧值, 新值) 合并
    }
    return s;
}

public synchronized void add(String sid, long gno) { maxGno.merge(sid, gno, Math::max); }
// synchronized：多线程安全（同一时刻只有一个线程能执行这个方法）

public synchronized String serialize() {
    StringBuilder sb = new StringBuilder();
    for (Map.Entry<String, Long> e : maxGno.entrySet()) {
        // entrySet()：拿到所有 [key, value] 对（≈ Object.entries）
        if (sb.length() > 0) sb.append(",");
        sb.append(e.getKey()).append(":1-").append(e.getValue());
    }
    return sb.toString();          // 空集合 → "" 空字符串
}

public synchronized void mergeFrom(GtidState other) { ... }
// 并入另一个集合（逐项 Math::max）——恢复时"一致性位点 ∪ 已应用"就用它

public synchronized LinkedHashMap<String, Long> snapshot() { return new LinkedHashMap<>(maxGno); }
// 拷一份只读视图，避免调用方直接改内部状态
```

### 5.15 `JdbcPkBoundaryScanner.java`（55 行）★红线 R6：分片扫描

**全量迁移和数据校验共用的分片算法**——两端必须切出完全相同的 chunk，才能逐片比对。

```java
public static List<Object> scanUpperBounds(Connection conn, String schema, String table,
                                           String pkColumn, int chunkSize) {
    String q = qualify(schema, table);                    // `schema`.`table`（带反引号）
    String sql = "SELECT " + quote(pkColumn) + " FROM " + q + " ORDER BY " + quote(pkColumn);
    // 只 SELECT 主键一列，按主键排序——扫描的是"键列表"，不是数据

    List<Object> uppers = new ArrayList<>();
    try (PreparedStatement ps = conn.prepareStatement(sql)) {
        streamFetch(conn, ps);                            // 设置流式读取（见下）
        try (ResultSet rs = ps.executeQuery()) {
            int n = 0;
            Object last = null;
            while (rs.next()) {                           // 逐行推进游标
                last = rs.getObject(1);                   // 记住当前主键值
                n++;
                if (n >= chunkSize) {
                    uppers.add(last);                     // 每数满 chunkSize 个，落一个上界
                    n = 0;
                }
            }
            if (n > 0) uppers.add(last);                  // 不足一片的尾巴也要一个上界
        }
    }
    ...
    return uppers;   // 例：主键 1..2500，chunkSize=1000 → [1000, 2000, 2500]
}
```

例：主键 1~2500、chunkSize=1000 → 返回 `[1000, 2000, 2500]`，即 3 个分片 `(,1000] (1000,2000] (2000,2500]`。
**为什么扫描"上界"而不是"边界对"**：第 i 片的上界就是第 i+1 片的下界，一个数组足够表达全部边界。

```java
public static String qualify(String schema, String table) { ... }   // 拼成 `s`.`t`
public static String quote(String id) { return "`" + id.replace("`", "``") + "`"; }
// 反引号包裹标识符防保留字冲突；标识符里的反引号翻倍转义——SQL 注入防御细节

static void streamFetch(Connection conn, PreparedStatement ps) throws SQLException {
    if (conn.getMetaData().getDatabaseProductName().toLowerCase().contains("mysql")) {
        ps.setFetchSize(Integer.MIN_VALUE);   // MySQL 驱动的"魔法值"：真正的行级流式读取
    } else {
        ps.setFetchSize(500);                 // H2 等：每次预取 500 行
    }
}
```

> **为什么流式**：千万行的表，默认 JDBC 会把整个 ResultSet **全部加载进内存**直接 OOM。MySQL 驱动里 `setFetchSize(Integer.MIN_VALUE)` 是开启逐行流的唯一姿势（驱动的历史设计，背下来即可）。千万级主键扫描内存占用恒定。

**`doWrite`——R4 的落实现场**（§1.7 讲过的标准手动事务模板）：

```java
private void doWrite(List<RowRecord> batch, String advanceGtidSet) throws SQLException {
    boolean oldAutoCommit = connection.getAutoCommit();   // 记住进来前的状态
    connection.setAutoCommit(false);                      // ① 开事务
    try {
        for (Run run : splitRuns(batch)) {                // ② 按"连续同表同操作"分组
            apply(run);                                   //    逐组执行 SQL
        }
        if (advanceGtidSet != null) {                     // ③ 增量：同一事务内更新位点
            TargetSchemaInit.updateCheckpoint(connection, taskId, advanceGtidSet);
        }
        connection.commit();                              // ④ 数据+位点一起提交
    } catch (SQLException e) {
        connection.rollback();                            // ⑤ 任一步失败，全部回滚
        throw e;
    } finally {
        connection.setAutoCommit(oldAutoCommit);          // ⑥ 恢复连接状态
    }
}
```

②③④ 合起来 = **数据与位点原子提交**。⑤ = 位点永远不会超前于数据。这就是"at-least-once 重放 + 幂等写入 = 效果 exactly-once"的分界线。

**`splitRuns`——R5 保序分组建批**：

```java
record Run(String table, boolean upsert, List<RowRecord> rows) {}
// "Run" = 连续相同性质的一段。record 也能定义在类内部（嵌套类型）

static List<Run> splitRuns(List<RowRecord> batch) {
    List<Run> runs = new ArrayList<>();
    for (RowRecord r : batch) {
        boolean upsert = r.op() == com.minidts.common.OpType.UPSERT;
        if (!runs.isEmpty()) {
            Run last = runs.get(runs.size() - 1);        // 看上一个 run
            if (last.table().equals(r.table()) && last.upsert() == upsert) {
                last.rows().add(r);                      // 同表同操作 → 并入当前 run（顺序不乱）
                continue;
            }
        }
        Run run = new Run(r.table(), upsert, new ArrayList<>());   // 否则开新 run
        run.rows().add(r);
        runs.add(run);
    }
    return runs;
}
```

为什么按"连续段"分组而不是全局 group by？——**保持全局顺序**。批内顺序 `(A表 upsert, B表 delete, A表 upsert)` 切成 3 个 run 依次执行，顺序不乱；如果全局合并成 2 组就重排了。顺序在增量回放里至关重要（同一行先删后插和先插后删结果不同）。

### 7.1 `TokenBucket.java`（48 行）——限速器

```java
private final long capacity;                 // 桶容量（= 每秒令牌数）
private final double refillPerNano;          // 每纳秒补几个令牌（capacity / 1e9）
private double tokens;                       // 当前令牌数（double：亚秒级补充）
private long lastRefillNanos;                // 上次补水的时间戳（System.nanoTime()，纳秒级时钟）
private final Lock lock = new ReentrantLock();
// 用显式锁而不是 synchronized：acquire 里要"解锁睡 10ms 再锁回来"，synchronized 做不到中途放锁

public TokenBucket(long rowsPerSecond) {
    this.capacity = Math.max(1, rowsPerSecond);
    this.refillPerNano = capacity / 1e9;     // 1e9 = 10^9（科学计数法字面量）
    this.tokens = capacity;                  // 开局满桶（允许小爆发）
    this.lastRefillNanos = System.nanoTime();
}

public void acquire(long n) {                // 申请 n 个令牌（搬 n 行之前调用）
    if (n <= 0) return;
    lock.lock();
    try {
        tokens = Math.min(capacity, tokens + (System.nanoTime() - lastRefillNanos) * refillPerNano);
        lastRefillNanos = System.nanoTime();
        // 惰性补水：不搞定时器，每次 acquire 时按"距上次过了多少纳秒"补足（上限桶容量）
        while (tokens < n) {                 // 不够 → 睡 10ms 再来
            lock.unlock();                   // 睡觉时必须放锁，否则别的线程全堵死
            try {
                Thread.sleep(10);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();   // 恢复中断标记（线程礼仪，§1.11）
                return;                              // 被中断 = 让我停，直接放弃申请
            }
            lock.lock();
            tokens = Math.min(capacity, tokens + ...);   // 醒来再补一次水
            lastRefillNanos = System.nanoTime();
        }
        tokens -= n;                         // 扣掉本次消耗
    } finally {
        lock.unlock();                       // 无论怎么退出都放锁
    }
}
```

> 惰性补水（lazy refill）是令牌桶的经典实现技巧：**不需要后台线程定时加水**，任何时刻需要用令牌时按时间差现算即可，无竞争、零开销。

```java
public void run() {
    ExecutorService executor = Executors.newFixedThreadPool(parallelism);
    // 线程池：parallelism 个工人
    String firstError = null;
    try (Connection metaConn = Connections.open(source)) {
        // ① 元数据校验（一条连接搞定，不进 worker）
        List<String> pks = PkResolver.resolvePkColumns(metaConn, schema, table);
        if (pks.size() > 1) throw new DtsException("复合主键暂不支持...");
        String pk = pks.get(0);
        String pkType = PkResolver.pkTypeName(metaConn, schema, table);
        if (!PkCodec.supported(pkType)) throw new DtsException("主键类型不支持: ...");
        // fail fast：不支持的场景在这里就炸，别跑到一半

        // ② 扫描分片上界（§5.15）
        List<Object> uppers = JdbcPkBoundaryScanner.scanUpperBounds(metaConn, schema, table, pk, chunkSize);

        // ③ 读断点：上次已完成的上界集合
        Set<String> completed = checkpointStore.completedUpperPks(taskId);

        TokenBucket limiter = new TokenBucket(rowsPerSecond);

        // ④ 逐片提交给线程池（并行度由池控制）
        List<Future<?>> futures = new ArrayList<>();
        for (int i = 0; i < uppers.size(); i++) {
            if (stopped) break;                      // 暂停检查点1：调度循环
            Object upper = uppers.get(i);
            String upperKey = PkCodec.encode(upper);
            if (completed.contains(upperKey)) {       // 断点续传：跳过已完成的片
                chunksSkipped.incrementAndGet();
                continue;
            }
            Object lower = i == 0 ? null : uppers.get(i - 1);   // 上片上界=本片下界
            Chunk chunk = new Chunk(i, lower, upper);
            futures.add(executor.submit(() -> copyChunk(chunk, pk, pkType, limiter)));
            // lambda 捕获局部变量 chunk/limiter；提交后立即返回 Future，不等执行
        }

        // ⑤ 等待全部完成；任何一片失败 → 记录首个错误并立刻 shutdownNow()（中断其余 worker）
        for (Future<?> f : futures) {
            try {
                f.get();                              // 阻塞到该任务结束；任务内异常在此重抛
            } catch (Exception e) {
                firstError = rootMessage(e);
                executor.shutdownNow();               // 发中断信号，让 worker 在停止检查点退出
                break;
            }
        }
    } catch (Exception e) {
        firstError = rootMessage(e);
    } finally {
        executor.shutdownNow();                       // 无论如何都关池
    }

    // ⑥ 结果上报
    if (firstError != null) notifier.onError(taskId, "全量失败: " + firstError);
    else if (!stopped) notifier.onFullDone(taskId);   // 正常跑完（被暂停则不上报）
}
```

> 注意 `pkType` 虽然传进了 `copyChunk` 但内部其实用编码后的字符串比较，类型信息主要由断点解码使用——读代码时看到"传了但用途在别处"是常事。

**`copyChunk`——搬一片**（每个 worker 并发执行）：

```java
private void copyChunk(Chunk chunk, String pk, String pkType, TokenBucket limiter) {
    if (stopped) return;                              // 暂停检查点2：worker 开工前
    String qualified = JdbcPkBoundaryScanner.qualify(schema, table);
    try (Connection src = Connections.open(source); Sink sink = sinkFactory.open()) {
        // 每个 worker 现场开自己的源连接和 Sink（try-with-resources 保证关闭）

        // 键集分页 SQL：第一片只有上界，其余片 (下界, 上界]
        String sql = chunk.lowerExclusive() == null
                ? "SELECT * FROM " + qualified + " WHERE `pk` <= ? ORDER BY `pk`"
                : "SELECT * FROM " + qualified + " WHERE `pk` > ? AND `pk` <= ? ORDER BY `pk`";
        // ↑ 实际代码用 JdbcPkBoundaryScanner.quote(pk) 拼反引号；这里简写

        List<RowRecord> records = new ArrayList<>();
        try (PreparedStatement ps = src.prepareStatement(sql)) {
            if (chunk.lowerExclusive() == null) {
                ps.setObject(1, chunk.upperInclusive());          // 1 个参数版
            } else {
                ps.setObject(1, chunk.lowerExclusive());          // 2 个参数版
                ps.setObject(2, chunk.upperInclusive());
            }
            ps.setFetchSize(chunkSize);
            try (ResultSet rs = ps.executeQuery()) {
                ResultSetMetaData md = rs.getMetaData();          // 结果集的元数据（几列、列名）
                int n = md.getColumnCount();
                List<String> cols = new ArrayList<>(n);
                for (int i = 1; i <= n; i++) cols.add(md.getColumnLabel(i));
                // 从查询结果反查列名（SELECT * 时不知道列顺序，问结果集要）
                while (rs.next()) {
                    List<Object> vals = new ArrayList<>(n);
                    for (int i = 1; i <= n; i++) vals.add(rs.getObject(i));
                    records.add(new RowRecord(schema, table, cols, vals, OpType.UPSERT,
                            "chunk-" + chunk.shardNo()));
                    // 全量读出的每一行都是 UPSERT；txId 填分片号（便于排查来源）
                }
            }
        }

        if (records.isEmpty()) {                      // 空片（数据在扫描后被删光等场景）
            checkpointStore.markChunkDone(taskId, chunk.upperKey());
            return;                                   // 空片也要记断点，否则恢复时反复重扫
        }

        sink.writeBatch(records, null);                        // ① 先写数据（位点 null = 全量无位点）
        checkpointStore.markChunkDone(taskId, chunk.upperKey()); // ② 再落断点——顺序是红线！
        rowsCopied.addAndGet(records.size());
        chunksDone.incrementAndGet();
        limiter.acquire(records.size());              // 按行数限速（搬完再扣令牌，不阻塞读）
    } catch (Exception e) {
        throw new DtsException("分片 " + chunk.shardNo() + " (≤" + chunk.upperKey() + ") 失败: "
                + rootMessage(e), e);
        // worker 里抛出 → run() 的 f.get() 捕获 → 任务转 ERROR
    }
}
```

**①② 的顺序为什么是铁律**：写完数据、还没记断点时崩溃 → 恢复后这片**重做**，靠 upsert 幂等收敛（多干活，不丢数据）。反过来（先记断点再写数据）→ 恢复后这片**跳过**，数据就永久丢了。**宁可重复，不可遗漏**——这是整类系统的根本取向。

**`rootMessage` 小工具**：沿着 `getCause()` 链一路挖到根因，取它的消息（异常层层包装时，最里层才是真正有用的信息）。

> 一个值得品味的边界情况（类注释写了）：全量扫描完边界后、拷贝中，源数据在变 → 某片实际行数和扫描时不同。没关系：增量会从一致性位点重放全量窗口内的全部变更兜底（R3），全量只管"尽力搬存量"。

### 8.2 `BinlogRecordMapper.java`（75 行）★R5：binlog 行 → RowRecord 的纯映射

**设计亮点**：把"翻译逻辑"从网络监听里剥出来，变成**无 IO 的纯函数**——不依赖真实 binlog 就能单测。

binlog 行事件给的是 `Serializable[]`（纯值数组，不带列名）。`Serializable` 是 Java 序列化接口，这里就是"能当值传输的东西"的笼统类型。

**核心：`update`——UPDATE 可能变出两条记录**：

```java
public static List<RowRecord> update(String schema, String table, List<String> columns,
                                    List<String> pkColumns, Serializable[] before, Serializable[] after,
                                    String txId) {
    List<RowRecord> out = new ArrayList<>(2);
    if (pkChanged(pkColumns, columns, before, after)) {
        out.add(record(schema, table, columns, before, OpType.DELETE, txId));   // 先删旧行
        out.add(record(schema, table, columns, after, OpType.UPSERT, txId));    // 再插新行
    } else {
        out.add(record(schema, table, columns, after, OpType.UPSERT, txId));    // 普通更新 → 一条 upsert
    }
    return out;
}
```

**为什么主键变更要拆两条**：upsert 语义是"按新主键写入"，如果源把 id 从 5 改成 6，只 upsert 新行的话目标库会同时存在 5 和 6 两行——错！必须先 DELETE 旧主键行，再 UPSERT 新主键行。且顺序固定（先删后增），恰好符合 R5 的"保序 + 拆删增"。

```java
private static boolean pkChanged(List<String> pkColumns, List<String> columns,
                                 Serializable[] before, Serializable[] after) {
    if (pkColumns == null || pkColumns.isEmpty()) return false;
    for (String pk : pkColumns) {
        int idx = columns.indexOf(pk);                 // 主键列在第几列
        if (idx < 0 || idx >= before.length || idx >= after.length) return false;
        Object b = before[idx];
        Object a = after[idx];
        if (b == null || a == null ? b != a : !normalizeKey(b).equals(normalizeKey(a))) {
            return true;
        }
        // ↑ 三元表达式嵌套，展开是：
        //   if (b==null || a==null) { 若 b!=a（一空一非空）→ 主键变了 }
        //   else                    { 若两个非空但不相等 → 主键变了 }
    }
    return false;
}

private static Object normalizeKey(Object v) {
    if (v instanceof Integer || v instanceof Short || v instanceof Byte || v instanceof Long) {
        return ((Number) v).longValue();
    }
    return v;
    // binlog 库对整数的反序列化类型不固定（可能 Integer 也可能 Long），
    // 归一成 Long 再 .equals 比较，否则 Integer(5).equals(Long(5)) 是 false！（装箱类型的 equals 陷阱）
}
```

> **Java 陷阱**：`Integer.valueOf(5).equals(Long.valueOf(5L))` 返回 **false**——不同包装类型 equals 必不相等。这是真实坑，normalizeKey 就是防它。

**事件处理 `handle(event)`——整个增量的心脏**。binlog 是事件流，一个事务长这样：

```
GTID事件(事务开始) → TABLE_MAP → WRITE_ROWS → ... → XID事件(提交)
```

```java
private void handle(Event event) throws Exception {
    EventHeader header = event.getHeader();          // 事件头（类型等）
    EventType type = header.getEventType();
    EventData data = event.getData();                // 事件体（按类型强转取细节）

    if (type == EventType.TABLE_MAP) {               // 表映射事件：记 tableId → 表名
        TableMapEventData tm = (TableMapEventData) data;
        tableById.put(tm.getTableId(), tm.getTable());

    } else if (type == EventType.GTID) {             // 事务开始：记下 GTID，开新缓冲
        currentGtid = ((GtidEventData) data).getGtid();
        txBuffer.clear();

    } else if (type == EventType.WRITE_ROWS || type == EventType.EXT_WRITE_ROWS) {
        // EXT_ 前缀 = MySQL 5.6+ 的新版事件（带额外标志位），两种都要处理
        WriteRowsEventData w = (WriteRowsEventData) data;
        for (Serializable[] row : w.getRows()) {     // 一个事件可含多行
            forTarget(w.getTableId(), (cols, name) ->
                    txBuffer.addAll(BinlogRecordMapper.write(schema, name, cols, row, currentGtid)));
            // forTarget：过滤+查元数据后执行动作（见下）；翻译结果进事务缓冲
        }

    } else if (type == EventType.UPDATE_ROWS || type == EventType.EXT_UPDATE_ROWS) {
        UpdateRowsEventData u = (UpdateRowsEventData) data;
        for (var entry : u.getRows()) {              // 每个元素是 before/after 一对
            Serializable[] before = entry.getKey();  // Map.Entry 的 key/value
            Serializable[] after = entry.getValue();
            forTarget(u.getTableId(), (cols, name) -> txBuffer.addAll(BinlogRecordMapper.update(
                    schema, name, cols, pkColumnsByTable.getOrDefault(name, List.of()),
                    before, after, currentGtid)));
            // getOrDefault：没有该表主键元数据时给空列表兜底
        }

    } else if (type == EventType.DELETE_ROWS || type == EventType.EXT_DELETE_ROWS) {
        ... 同 WRITE，调 BinlogRecordMapper.delete，传 before ...

    } else if (type == EventType.XID) {              // 事务提交：冲刷缓冲
        flushTx();
    }
    // 其余事件（QUERY/ROTATE/FORMAT_DESCRIPTION 等）非数据事件，忽略
}
```

**`forTarget(tableId, action)`——过滤 + 元数据保护壳**：

```java
private void forTarget(long tableId, TableAction action) throws Exception {
    String name = tableById.get(tableId);
    if (name == null || !inScope(name)) {            // 不在任务范围内（别的库/表）→ 跳过
        eventsSkippedOtherTables.incrementAndGet();
        return;
    }
    List<String> cols = columnsByTable.get(name);
    if (cols == null) {
        throw new DtsException("表 " + name + " 缺少列元数据（任务运行中新增表？），请重启任务重载元数据");
        // 显式报错而非静默跳过：新表没元数据，行数组的含义无法解释，跳过=丢数据
    }
    action.accept(cols, name);                       // 执行传入的动作（lambda）
}
```

`TableAction` 是文件里自定义的双参函数式接口（`void accept(List<String>, String) throws Exception`）——因为 JDK 自带的 `BiConsumer` 不允许抛受检异常，只好自己定义一个。

**`flushTx()`——事务落库（XID 时触发）**：

```java
void flushTx() throws Exception {
    if (currentGtid == null) {                       // 没见过 GTID 事件 = 源库没开 GTID
        LOG.warning("事务无 GTID（gtid_mode 未开？），跳过——环境预检应已拦截");
        return;                                      // LOG = java.util.logging.Logger，JDK 自带日志
    }
    try {
        String[] sidGno = currentGtid.split(":");    // "uuid:23" → ["uuid", "23"]
        appliedGtids.add(sidGno[0], Long.parseLong(sidGno[1]));   // 先推进内存中的已应用集合
        sink.writeBatch(txBuffer, appliedGtids.serialize());
        // ★ 关键：把序列化后的 GTID 集合传给 Sink → 与数据【同事务】写进目标库（R4）
        txApplied.incrementAndGet();
    } finally {
        txBuffer.clear();                            // 成功失败都清缓冲（失败重放由位点保证）
    }
}
```

**为什么"客户端单线程回调"很重要**（字段注释写了）：binlog 库用**一个线程**顺序回调事件 → `txBuffer`/`currentGtid` 这些普通字段天然串行无竞争，**事务内保序免费获得**（R5）。这是选型带来的架构红利。

**`buildClient`——伪装从库**：

```java
private BinaryLogClient buildClient(String resumeFromGtid) throws IOException {
    URI uri = URI.create(source.url().replaceFirst("^jdbc:", ""));
    // "jdbc:mysql://host:3306/db" → "mysql://host:3306/db"，再用 URI 解析出 host/port
    BinaryLogClient c = new BinaryLogClient(
            uri.getHost(), uri.getPort() == -1 ? 3306 : uri.getPort(), source.user(), source.password());
    c.setServerId((int) (System.currentTimeMillis() % 100000) + 1);
    // serverId：每个"从库"要有唯一 id，用时间戳取模生成随机 id（多实例不撞车）
    c.setKeepAlive(true);                            // 心跳保活
    if (resumeFromGtid != null && !resumeFromGtid.isBlank()) {
        c.setGtidSet(resumeFromGtid);                // 断点续传：从指定 GTID 集合之后开始拉
    } else {
        c.setGtidSet(currentGtidExecuted());         // 全新启动：从源库当前 gtid_executed 开始
    }
    return c;
}
```

`setGtidSet` 的语义是"这些事务我已消费过，请从这**之后**发给我"——这正是 GTID 断点的全部魔法。

**`preloadTableMetadata`**：开一条普通连接，对范围内每张表调 `PkResolver.resolveColumns / resolvePkColumns`，构建两张不可变 Map 后整体替换字段。**DDL 变更不处理**（README 已声明局限）——运行中加列会因列元数据缺失而显式报错，即 `forTarget` 里那个 throw。

### 9.2 `VerifyService.java`（175 行）★对账主流程

**两层策略**：先用 CRC 粗筛（快），不一致才逐行比（慢）——大表全量逐行比对太贵。

**`verify(taskId)` 主流程**：

```java
public VerifySummary verify(String taskId) {
    reportStore.clearTask(taskId);                   // 清掉上次校验报告
    try (Connection src = Connections.open(source); Connection tgt = Connections.open(target)) {
        List<String> pks = PkResolver.resolvePkColumns(src, schema, table);
        if (pks.size() > 1) throw new DtsException("复合主键暂不支持校验: " + pks);
        String pk = pks.get(0);

        // ★ R6：与全量共用同一个扫描器 + 同一 chunkSize → 两端分片完全一致
        List<Object> uppers = JdbcPkBoundaryScanner.scanUpperBounds(src, schema, table, pk, chunkSize);

        List<RowDiff> allDiffs = new ArrayList<>();
        int equal = 0;
        for (int i = 0; i < uppers.size(); i++) {
            Object lower = i == 0 ? null : uppers.get(i - 1);
            Object upper = uppers.get(i);

            ChunkCrc a = chunkCrc(src, pk, lower, upper);   // 源端分片 CRC
            ChunkCrc b = chunkCrc(tgt, pk, lower, upper);   // 目标端同范围 CRC
            boolean chunkEqual = a.count == b.count && a.crc == b.crc;
            // 行数也要相等（CRC 撞车概率极低但行数是免费的第二道保险）

            List<RowDiff> diffs = List.of();
            boolean realMismatch = false;
            if (!chunkEqual) {
                diffs = diffChunk(src, tgt, pk, lower, upper);            // 逐行比对找差异
                realMismatch = !diffs.isEmpty() && diffStillReal(src, tgt, pk, lower, upper, diffs);
                // 二次重读仍不一致才算真差异（防"校验瞬间源在写"的漂移误报）
                if (!realMismatch) diffs = List.of();                     // 假差异清空
            }
            reportStore.saveChunkResult(taskId, i, PkCodec.encode(upper),
                    chunkEqual || !realMismatch, a.crc, b.crc, diffs);    // 落报告
            if (realMismatch) allDiffs.addAll(diffs);
            else equal++;
        }
        allDiffs.addAll(targetOnlyBeyond(src, tgt, pk, uppers.isEmpty() ? null : uppers.get(uppers.size() - 1)));
        // 分片都以【源】的主键为界——目标库里比源最大主键还大的行不在任何片里，单独扫一遍兜底
        return new VerifySummary(uppers.size(), equal, uppers.size() - equal, allDiffs);
    } catch (SQLException e) { throw new DtsException("校验失败: ...", e); }
}
```

**`chunkCrc`——一个分片的校验和**：

```java
record ChunkCrc(long crc, int count) {}       // CRC 值 + 行数

private ChunkCrc chunkCrc(Connection conn, String pk, Object lower, Object upper) throws SQLException {
    StringBuilder sb = new StringBuilder();
    int count = 0;
    for (EncodedRow row : readChunk(conn, pk, lower, upper)) {
        if (count > 0) sb.append(RowCodec.COL_SEP);   // 行间也用 \u0001 分隔
        sb.append(row.encoded);                       // 行的编码串
        count++;
    }
    return new ChunkCrc(RowCodec.crc32(sb.toString()), count);
    // 整片 = 所有行编码串拼接后再 CRC。任何一行任何一列不同 → CRC 几乎必变
}
```

**`readChunk`——读一个分片并逐行编码**：

SQL 与全量 copyChunk 完全同款（键集范围 + ORDER BY）。差别在于把每行变成 `EncodedRow(pk编码, 整行编码)`：

**`diffChunk`——逐行精确比对**：

```java
private List<RowDiff> diffChunk(Connection src, Connection tgt, ...) throws SQLException {
    Map<String, String> s = toMap(readChunk(src, pk, lower, upper));   // 源片：pk编码 → 行编码
    Map<String, String> t = toMap(readChunk(tgt, pk, lower, upper));   // 目标片同构
    List<RowDiff> diffs = new ArrayList<>();
    for (Map.Entry<String, String> e : s.entrySet()) {
        String tv = t.get(e.getKey());
        if (tv == null) diffs.add(new RowDiff(e.getKey(), DiffType.MISSING, e.getValue(), null));
        // 源有目标无 → 缺失
        else if (!tv.equals(e.getValue())) diffs.add(new RowDiff(e.getKey(), DiffType.VALUE_DIFF, ...));
        // 都有但编码不同 → 值不同（★ R1 的价值：比较的是规范化编码，表示差异已被排除）
    }
    for (Map.Entry<String, String> e : t.entrySet()) {
        if (!s.containsKey(e.getKey())) diffs.add(new RowDiff(e.getKey(), DiffType.TARGET_ONLY, null, e.getValue()));
        // 目标有源无 → 多余
    }
    return diffs;
}
// toMap 用 LinkedHashMap（保持主键顺序，报告可读）
```

**`diffStillReal`——漂移二次确认**：

```java
private boolean diffStillReal(..., List<RowDiff> diffs) throws SQLException {
    if (diffs.isEmpty()) return true;
    List<RowDiff> recheck = diffChunk(src, tgt, pk, lower, upper);   // 再比一遍
    return !recheck.isEmpty();
    // 第一次有差异、第二次没有 → 校验瞬间数据在变（漂移），不算真差异
    // 两次都有 → 真不一致。（严格说二次比对应只针对首次差异的行，demo 简化为整片重比）
}
```

```java
private static final Map<TaskState, Set<TaskState>> ALLOWED = Map.of(
        TaskState.INIT, Set.of(TaskState.RUNNING_FULL),
        TaskState.RUNNING_FULL, Set.of(TaskState.FULL_DONE, TaskState.PAUSED, TaskState.ERROR),
        TaskState.FULL_DONE, Set.of(TaskState.RUNNING_INCR, TaskState.PAUSED, TaskState.ERROR),
        TaskState.RUNNING_INCR, Set.of(TaskState.FINISHED, TaskState.PAUSED, TaskState.ERROR),
        TaskState.PAUSED, Set.of(TaskState.RUNNING_FULL, TaskState.RUNNING_INCR),
        TaskState.ERROR, Set.of(TaskState.RUNNING_FULL, TaskState.RUNNING_INCR),
        TaskState.FINISHED, Set.of());
// Map.of：不可变 Map（键值对参数交替）。整张迁移表 = 一行数据，一目了然
// PAUSED/ERROR 只能回运行态（回哪个由 resumeTo 决定），FINISHED 哪也去不了

public static void transition(TaskState from, TaskState to) {
    if (from == to) throw new DtsException("状态自迁移无意义: " + from);
    if (!ALLOWED.getOrDefault(from, Set.of()).contains(to)) {
        throw new DtsException("非法状态迁移: " + from + " → " + to + "（允许: " + ALLOWED.get(from) + "）");
    }
    // 只校验不执行——真正的状态落库由调用方做。"守卫函数"风格
}

public static TaskState resumeTo(boolean fullDone) {
    return fullDone ? TaskState.RUNNING_INCR : TaskState.RUNNING_FULL;
    // 恢复去哪：全量没完 → 重跑全量（断点跳片）；完了 → 直接增量（GTID 续播）
}

public static boolean isTerminal(TaskState s) { return s == TaskState.FINISHED; }
```

```java
        // ★ 全项目唯一一次 new 数据面/引擎实例：MigrationEngineImpl 在这里被组装并交给容器，
        //   TaskController 构造器注入的就是它。整个系统的"总装"就这几十行
    }
}
```

> **为什么 cm 的类不直接标 @Component 让 Spring 自动扫描**？——cm/full/store 等模块**有意不依赖 Spring**（看它们的 import，全是 JDK + common），这样才能脱离框架单测。装配的脏活全部集中在 starter，这就是"端口适配器"的适配层。

```java
public synchronized void start(String taskId) {
    // synchronized：REST 并发点击 start/pause/resume 时串行化（简单但够用的并发控制）
    TaskMetadata t = load(taskId);
    if (t.state() == RUNNING_FULL || t.state() == RUNNING_INCR) throw new DtsException("任务已在运行中");

    if (t.state() == TaskState.INIT) {
        TaskStateMachine.transition(t.state(), TaskState.RUNNING_FULL);     // 先过状态机守卫
        String consistency = readConsistency(t);
        // ★ R3：全量开始前读 gtid_executed 存进元数据（consistency_gtid 字段）
        tasks.updateConsistencyGtid(taskId, consistency);
        tasks.updateState(taskId, TaskState.RUNNING_FULL, false, null);
        launchFull(t.withFullDone(false, consistency));
        // withFullDone：复制出新元数据对象（带上刚记的位点）再传给数据面
    } else if (t.state() == TaskState.FULL_DONE) {
        ... 直接 launchIncr(t, t.consistencyGtid()) ...    // 从 FULL_DONE 手动 start = 只跑增量
    } else {
        throw new DtsException("当前状态 ... 不可 start（PAUSED/ERROR 请用 resume）");
    }
}
```

**`pause` / `resume` / `finish`**：

```java
public synchronized void pause(String taskId) {
    TaskMetadata t = load(taskId);
    TaskStateMachine.transition(t.state(), TaskState.PAUSED);       // 非运行态 pause → 409
    Runtime rt = runtimes.get(taskId);
    if (rt != null) {
        if (rt.full() != null) rt.full().stop();    // 全量：置 volatile stopped=true，worker 在检查点退出
        if (rt.store() != null) rt.store().stop();  // 增量：断开 binlog 连接
    }
    tasks.updateState(taskId, TaskState.PAUSED, t.fullDone(), null);
    // 暂停不丢进度：全量断点在 H2，增量位点在目标库，fullDone 标记照实记录
}

public synchronized void resume(String taskId) {
    TaskMetadata t = load(taskId);
    TaskState to = TaskStateMachine.resumeTo(t.fullDone());   // 该回全量还是增量？
    TaskStateMachine.transition(t.state(), to);
    if (to == TaskState.RUNNING_FULL) {
        launchFull(t);                                // 全量重来（断点片自动跳过）
    } else {
        String resumeGtid = incrResumePoint(t);       // ★ 增量恢复点（见下）
        launchIncr(t, resumeGtid);
    }
}

public synchronized void finish(String taskId) {
    TaskStateMachine.transition(t.state(), TaskState.FINISHED);   // 只有 RUNNING_INCR 能到 FINISHED
    ...stop store...；updateState(FINISHED)；runtimes.remove(taskId);
}
```

**`incrResumePoint`——增量恢复点的取法**（整个断点体系的关键一跳）：

```java
private String incrResumePoint(TaskMetadata t) {
    String ckpt = incrResumePointQuiet(t);            // 去目标库 dts_incr_checkpoint 查
    return ckpt != null ? ckpt : t.consistencyGtid(); // 没写过位点（还没进过增量）→ 回退一致性位点
}
// 位点 < 数据（R4 同事务保证），从位点重播会重复但不丢；Sink 幂等把重复消化掉
```

**`onFullDone`——数据面回调（自动接增量）**：

```java
@Override
public void onFullDone(String taskId) {
    TaskMetadata t = load(taskId);
    if (t.state() != TaskState.RUNNING_FULL) return;   // 已被 pause / 重复回调 → 忽略（幂等回调）
    TaskStateMachine.transition(RUNNING_FULL, FULL_DONE);
    tasks.updateState(taskId, TaskState.FULL_DONE, true, null);
    TaskStateMachine.transition(FULL_DONE, RUNNING_INCR);
    tasks.updateState(taskId, TaskState.RUNNING_INCR, true, null);
    launchIncr(load(taskId), t.consistencyGtid());
    // ★ 从【一致性位点】起播——全量期间的写入全部重放，幂等收敛。R3 的闭环点
}

@Override
public void onError(String taskId, String reason) {
    TaskMetadata t = tasks.find(taskId).orElse(null);
    if (t == null || t.state() == TaskState.FINISHED) return;
    try {
        TaskStateMachine.transition(t.state(), TaskState.ERROR);
        tasks.updateState(taskId, TaskState.ERROR, t.fullDone(), reason);
    } catch (DtsException ignored) {
        // PAUSED/FINISHED 下的迟到失败回调：保留现场，不改状态
    }
}
```

**`launchFull`——多表串行 + 单表内并行**：

```java
private void launchFull(TaskMetadata t) {
    int totalTables = t.tables().size();
    java.util.concurrent.atomic.AtomicInteger completed = new java.util.concurrent.atomic.AtomicInteger();
    // 原子计数器：数"完成了几张表"

    TaskStateNotifier agg = new TaskStateNotifier() {       // 匿名内部类：现场实现接口（≈ 内联对象）
        @Override public void onFullDone(String taskId) {
            if (completed.incrementAndGet() == totalTables) {
                MigrationEngineImpl.this.onFullDone(taskId);
                // 聚合器：所有表都回调完成，才真正推进状态（单表时 == 立即成立，退化成直通）
            }
        }
        @Override public void onError(String taskId, String reason) {
            MigrationEngineImpl.this.onError(taskId, reason);   // 错误直通
        }
    };

    FullTransferService first = fullServiceFor(t, t.tables().get(0), agg);
    Thread thread = new Thread(() -> {
        try {
            first.run();                                     // 第 1 张表
            for (int i = 1; i < totalTables; i++) {
                if (load(t.id()).state() != TaskState.RUNNING_FULL) return;
                // 每张表之间检查状态：被暂停/出错就不继续
                FullTransferService svc = fullServiceFor(t, t.tables().get(i), agg);
                runtimes.put(t.id(), new Runtime(svc, null));  // 更新句柄（pause 要能停到当前表）
                svc.run();
            }
        } catch (Exception e) { onError(t.id(), e.getMessage()); }
    }, "full-" + t.id());                                    // 给线程起名（排查时能认出来）
    runtimes.put(t.id(), new Runtime(first, null));
    thread.start();
}
// 设计取舍：表间串行（避免多表同时全量打爆源库）、表内并行（parallelism 个 worker 抢分片）
```

`fullServiceFor`：组装一个表的 FullTransferService，其中 SinkFactory 传 `() -> new MySqlSink(Connections.open(...), id, pkMap(t))`——每开一个 worker 就现开一条目标连接。

**`launchIncr`**：

```java
private void launchIncr(TaskMetadata t, String resumeGtid) {
    BinlogStoreService store = new BinlogStoreService(source端点, t.schema(), t.tables(), t.id(), this);
    // 注意第 5 个参数传 this：引擎自己就是 TaskStateNotifier
    Thread thread = new Thread(() -> store.start(resumeGtid, () -> {   // Sink 惰性创建
        try { return new MySqlSink(Connections.open(目标端点), t.id(), pkMap(t)); }
        catch (Exception e) { throw new DtsException("打开目标连接失败: ...", e); }
    }), "incr-" + t.id());
    runtimes.put(t.id(), new Runtime(null, store));
    thread.start();
}
```

```java
public Map<String, Object> verify(String taskId) {
    TaskMetadata t = load(taskId);
    Map<String, Object> out = new LinkedHashMap<>();
    boolean allEqual = true;
    for (String table : t.tables()) {                     // 逐表建 VerifyService（同 chunkSize，R6）
        VerifyService svc = new VerifyService(源端点, 目标端点, t.schema(), table, t.chunkSize(), verifyReports);
        VerifySummary s = svc.verify(taskId);
        allEqual &= s.allEqual();                         // &= 布尔与自赋值（allEqual = allEqual && ...）
        Map<String, Object> per = new LinkedHashMap<>();
        per.put("chunks", s.chunks()); per.put("equal", s.equalChunks()); ...
        if (!s.allEqual()) per.put("diffs", s.diffs().stream().map(String::valueOf).limit(50).toList());
        // 差异最多展示 50 条（String::valueOf：调用每个元素的 toString）
        out.put(table, per);
    }
    out.put("allEqual", allEqual);
    return out;                                           // 这个 Map 直接变成 HTTP JSON 响应
}
```

## 13. 六条红线串讲：整个系统如何协同

现在把 README 的 6 条"红线"用你已经读过的代码串一遍——能自己讲出这六段话，就等于吃透了整个项目：

**R1 · 双端共用 RowCodec（§5.9）**
校验比对的是编码串，源端 `chunkCrc` 和目标端 `chunkCrc` 调的是同一个 `RowCodec.encode`。类型归一（Values）+ 编码规则（标签、补零、禁科学计数法）保证"同一行数据在两端必得同一串"。若两端各写一套编码，时区/浮点/格式的微小差异会天天报假不一致。

**R2 · 位点表建在目标库（§6.2）**
`dts_incr_checkpoint` 由 `TargetSchemaInit.ensure` 建在**目标业务库**——和数据同库，才可能同事务。建在别处（比如 CM 的 H2），事务边界就断了。

**R3 · 一致性位点而非缓存 binlog（§5.13、§11.3）**
`start` 在**全量开始前**读 `gtid_executed` 存入 `consistency_gtid`；全量完成后增量从**这个位点**起播（`onFullDone` → `launchIncr(t, t.consistencyGtid())`）。于是全量搬运期间源库的所有写入都必然被增量重放——不缓存任何 binlog 数据，只记一个编号，简单且不丢不漏。

**R4 · 数据+位点同事务（§6.3）**
`MySqlSink.doWrite`：`setAutoCommit(false)` → 写数据 → `updateCheckpoint` → `commit`。位点永远不超前于数据；崩溃恢复从位点重播=至少一次；配合 upsert 幂等=效果恰好一次。增量恢复点取法（§11.3 `incrResumePoint`）= 目标库位点 ?? 一致性位点。

**R5 · 保序 + PK 更新拆删增（§6.3、§8.2）**
binlog 客户端单线程回调 → 事务天然串行；事务内 `splitRuns` 按"连续同表同操作"分组不重排；主键变更的 UPDATE 被 `BinlogRecordMapper.update` 拆成"先 DELETE 后 UPSERT"两条有序记录。

**R6 · 校验复用全量分片算法（§5.15、§9.2）**
`VerifyService` 与 `FullTransferService` 用同一个 `JdbcPkBoundaryScanner.scanUpperBounds` + 同一 `chunkSize`（都取自任务元数据），源端切的片在两端逐片对齐。

**一次完整任务的时间线**（把六条红线按时间串起来）：

```
createTask   → 环境预检(§8.1) + 主键一致性校验 + 目标库建系统表[R2]
start        → 记一致性位点[R3] → 状态 INIT→RUNNING_FULL
全量 run()   → 扫描分片[R6] → 多 worker 拷片 → 每片: 先写数据再记断点
全量完成     → onFullDone → 状态→RUNNING_INCR → 增量从一致性位点起播[R3]
增量循环     → GTID..XID 聚合[R5] → Sink 同事务写数据+位点[R4] → 编码统一[R1]
pause/resume → 全量跳过断点片 / 增量从目标库位点续播
verify       → 同一分片算法两端 CRC[R6] → 不一致逐行比 → 漂移二次过滤
finish       → RUNNING_INCR → FINISHED（终态）
```
