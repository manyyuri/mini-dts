# OMS 对照学习地图：用 mini-dts 当探针，逐个问「为什么非要这样」

> 目标不是把 mini-dts 做成 OMS，而是**用最小实现去撞出 OMS 的设计理由**。
> 每个决策点三行：**OMS 怎么做 → 不这么做会怎样 → 用 mini-dts 怎么验证**。
> 前两行是知识，第三行是唯一能留下长期记忆的动作。

---

## 一、先立一个坐标系：OMS 一条链路的六段

```
① 接入与评估（预检查 / 迁移评估）
        ↓
② 结构迁移（DDL 转换 + 类型映射）
        ↓
③ 全量迁移（切片 + 并行 + 断点）
        ↓
④ 增量同步（按源类型抓取变更 + 幂等写入）
        ↓
⑤ 数据校验（分片 CRC / 抽样 / 增量校验）
        ↓
⑥ 控制面（任务生命周期 + 调度 + 高可用 + 多节点）
```

以后任何一个需求、任何一个 bug，都先问：**它落在哪一段？** 这一步能把讨论从"感觉"
变成"定位"。（这也是课程 [`0012 改造演练`](../lessons/0012-refactor-oms.md) 那张矩阵的用法。）

## 二、十个决策点（对照表）

| # | 决策点 | OMS 怎么做 | 不这么做会怎样 | 用 mini-dts 验证（探针实验） |
|---|---|---|---|---|
| 1 | **组件拆分** | CM / 结构迁移 / 全量 / 增量（Store+Connector）/ 校验分开部署 | 一次全量把进程撑死，增量也被拖死；组件无法各自伸缩 | 课程 L12：把运行时表从内存搬到 DB，体会「状态搬家」的代价 |
| 2 | **变更抓取按源类型分实现** | MySQL→binlog、Oracle→LogMiner、OB→OBLogProxy、PG→逻辑复制 | 想做「一个通用抓取器」= 无底洞；各源日志机制根本不通用 | 给 mini-dts 加一个假源（如文件回放）当第二个 Store 实现，感受接口该长什么样 |
| 3 | **一致性位点而非锁表** | 记录源端一致性位点，全量期间不阻塞业务 | 锁表 = 业务停摆；不记位点 = 全量期间的写入永久丢失 | L8 + L9：把位点从"全量之后"改成"全量之前"，跑一遍看差异 |
| 4 | **数据与位点同事务** | 位点与业务数据同库同事务提交 | 位点超前 → 丢一段；位点落后 → 重放（可接受） | 已有：把 `MySqlSink` 拆成两个事务，单测立刻红 |
| 5 | **能力矩阵（谁能迁到谁）** | 每个源类型带 `enableMigrationDest` / `enableSyncDest` 白名单 | 任意→任意 = 组合爆炸，每个组合都要有人维护与测试 | 给 mini-dts 写 1 页矩阵（它其实只有 MySQL→MySQL 一条） |
| 6 | **结构迁移独立成段** | DDL 转换 + 类型映射 + 不兼容项报告，需要人确认 | 把 DDL 转换塞进数据链路 → 一次转换失败整条任务停；且没人敢确认 | L11 扩展：让 ADD COLUMN 跨方言翻译，体会"白名单为什么只有一种语句" |
| 7 | **DDL 转换必然有损** | 提前给「不兼容项 / 改造建议」 | 承诺"自动转换一切"= 迁移后期集体返工 | 把 MySQL `unsigned` / `tinyint(1)` / `enum` 试着映射到 PG，看哪几个必然要人决定 |
| 8 | **校验做成分片 CRC + 分级** | 分片 CRC、抽样、增量校验，可分级降成本 | 全表逐行比在大表上根本跑不完，校验被跳过 = 等于没有 | L7 + L2：把编码口径改一处，看假差异怎么爆发 |
| 9 | **断点/位点跟着数据走** | 断点放目标端或共享可靠存储 | 换节点断点丢失 → 大表从头搬 | L10：把断点放回控制面本地磁盘，重启一次看结果 |
| 10 | **迁移期要能回退（反向增量）** | 支持反向增量/双写，切换窗口内可退回 | 切到新库发现问题只能硬扛，没有退路 | 思考题：mini-dts 位点与幂等能不能支撑"反向再跑一条"？（答案在 L6 主键变更那条） |

## 三、怎么用这张表（一次只做一个格子）

1. 选一个格子（推荐从 **#5 能力矩阵** 开始，零代码成本）。
2. 先自己写出「OMS 为什么这么做」，再翻课程/代码验证。
3. 能改的格子就动手改 mini-dts**一小块**（半天内能跑完测试的粒度）。
4. 改完立刻写一句结论到 `learning-records/`：**我原来以为…，实际是…，所以…**。

## 四、五个「不得不」（学完应该能脱口而出）

1. **不得不拆组件**：全量是 IO 密集、增量是长连接、校验是可暂停的批处理，三者的伸缩与故障模式不同。
2. **不得不按源类型分实现**：binlog / redo / clog / wal 是四种完全不同的日志机制，没有通用抽象。
3. **不得不做能力矩阵与预检查**：组合爆炸 + 失败成本随时间指数上升（课程 `0015` 六道闸门）。
4. **不得不承认 DDL 转换有损**：两种数据库的类型系统不能完全互映，必须留人工决策点。
5. **不得不做分片 CRC**：大表逐行比不可承受，而"不校验"等于没有校验。

## 五、mini-dts 刻意**不**照抄的部分（差异也是知识）

| OMS 有 | mini-dts 没有 | 这说明了什么 |
|---|---|---|
| 多源多目标 + 矩阵 | 只有 MySQL→MySQL | 产品能力边界是被**维护成本**决定的，不是被技术决定 |
| 结构迁移（DDL 转换） | 要求目标表已存在且结构一致 | 把最难的部分（类型系统）外包给了人 |
| 分布式调度 + 多节点 | 单进程 + 租约 | 分布式不是为了性能，是为了**故障域隔离与接管** |
| 反向增量 / 双活 | 无 | 迁移是一次性事件 vs 迁移是一个**可回退的过程** |
