0001mini-oms 重讲：从「一条数据的旅程」看它到底在干嘛

三条通道全量（搬存量）、增量（跟变化）、校验（对清单）
控制面只管任务的一生：参数、状态、谁在跑
目标库自用表增量进度、全量进度、死信、DDL 台账、结构指纹
不丢不重靠三件事断点宁可靠后、幂等 UPSERT、数据与位点同事务
一句话源库照常跑业务，我在旁边搬，并随时说清搬到哪了

0002L2 数据契约：三个通道共用一套「行」的写法

行结构schema/table/columns/values/op/txId
编码出口只有一个：RowCodec
归一化时间精度、小数 scale、binary→hex、NULL 标记
顺序columns 顺序 = 定义顺序，三处一致
失败策略列数≠值数 → 直接报错

0003L3 主键即一切：切片、断点、幂等、校验共用一个上界

切法按主键范围，每片记上界
区间左开右闭 `(lo, hi]`
断点键上界的编码值
已完成的判据上界在断点集合里
拒绝条件无主键 / 复合主键 / 主键类型不支持

0004L4 幂等写入与保序：同一行写几次都一样

幂等写法`INSERT … ON DUPLICATE KEY UPDATE`
前提目标端主键与源一致
合并规则只合并相邻、同表、同操作
上限单条语句 ≤ 500 行
失败兜底逐行重试一次，仍失败落死信表

0005L5 全量通道：切片、并行、限速，以及那个「糟糕但安全」的窗口

顺序红线先写数据，后记断点
并行边界只在片之间
断点位置目标库 `oms_full_checkpoint`
限速实例级 + 任务级两层令牌桶
恢复语义跳过已完成上界，重做未记的那一片

0006L6 增量通道：一串 binlog 事件，怎么变成一批「行」

批边界GTID … XID 一个事务一批
顺序批内保持源库到达顺序
主键变更DELETE 旧行 + UPSERT 新行
大事务缓冲上限，超了先落一批（位点不动）
表过滤库名 + 表名双键

0007L7 校验通道：怎么证明「搬对了」，又怎么不被线上写入骗

切法与全量完全一致
第一层分片 CRC 比快
第二层不一致的分片重读、逐行比
输出差异表：分片号 + 主键 + 两侧行
定位只发现问题，不改数据

0008L8 位点与 GTID：为什么要记一个「起点」，而不是录下 binlog

位点类型GTID 集合（`uuid:1-n`）
一致性位点全量开始**前**读取
增量起点全量完成 → 从一致性位点回放
存放位置目标库 `oms_incr_checkpoint`
环境要求`gtid_mode=ON`（建任务时预检）

0009L9 数据 + 位点同事务：不丢数据的最后一道保险

原子单位一个源事务 = 一个目标事务
事务内含业务写入 + 位点更新
失败处理整体回滚，位点不动
位点位置目标库（同库才能同事务）
可证明性质位点绝不超前，进程恢复后最多重做

0010L10 崩溃与接管：全系统一共三处「状态」，都在哪、谁读

断点（全量）目标库，按分片上界
位点（增量）目标库，与数据同事务
租约元数据库，心跳续租
接管抢租约 → 读断点 → 跳过已完成
假活状态在跑但指标不动 = 故障

0011L11 DDL 与结构漂移：源端改了表，同步怎么办

DDL 在哪binlog 的 QUERY 事件
白名单纯追加列，自动执行
其它 DDL记台账 + 任务暂停等人
台账目标库 `oms_ddl_event`（含语句原文）
指纹建任务登记，运行期复核

0012L12 改造演练：三个需求，各会牵动哪些模块

事实归属这个信息现在存在哪？谁读？
契约变更端口签名要不要变？`RowRecord` 要不要加字段？
语义重做目标端写语义是否要重做（如 Kafka 无 UPSERT）
状态搬家内存状态是否要落库（多进程前提）
测试成本哪些现有测试会失效？要补哪一层？

0013E1 这类系统怎么测：三层，各抓一类毛病

H2 双库逻辑正确性，秒级反馈
崩溃注入「写了没记断点」窗口的证明
Docker E2E真实 binlog / 重连 / 接管
门控无 Docker 自动跳过，不阻塞本地开发

0014E2 线上视角：四个指标，一眼看出「真在跑」还是「假活着」

必看 4 指标state / rowsCopied / incrCheckpointGtid / incrReconnects
健康判据指标在动，不只是状态在跑
假活定义状态 RUNNING + 指标冻结
设计红线失败必须可见，宁可报红不要静默

0015E3 建任务时的六道闸门：把事故挡在开始之前

时机全部在 `createTask`，只查元数据
原则能早拒就早拒
静默风险库名、结构漂移
指纹建任务登记、运行期复核
成本毫秒级，值得
