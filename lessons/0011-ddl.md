# L11 DDL 与结构漂移：源端改了表，同步怎么办

> DDL 藏在 binlog 的 QUERY 事件里。老实现整类忽略这些事件，等于把结构变更全部丢掉；现在的处置是三条路。

## 为什么这节重要

结构变化是「静默破坏」的典型：数据行本身没错，但列变了、类型变了，写入就开始错位或失败。
这类问题不会自己暴露，只会在某天你发现「有几列的值串了」。

![DDL 的三条分岔路](../assets/puml/fig4-ddl.png)

## 三条路

| 分类 | 判定 | 处置 |
|---|---|---|
| 忽略 | `BEGIN` / `COMMIT` / `SET …` | 不是结构变更 |
| **白名单：纯追加列** | `ALTER TABLE t ADD [COLUMN] c …` | 目标端自动执行 → 重读结构 → 更新指纹 → 继续同步 |
| 其余 DDL | `MODIFY` / `DROP` / `RENAME` / `CREATE` / `TRUNCATE` / `ADD INDEX` | 记台账 `oms_ddl_event` → 任务转「暂停」等人确认 |

为什么白名单只放「追加列」：它只加列、不动既有数据，风险可控且可自动重放。
`DROP`/`MODIFY` 之类的破坏性变更，一旦自动执行可能造成不可逆损失，必须人看一眼。

## 结构指纹：挡住 binlog 之外的漂移

建任务时给每张表算一个指纹（列名 + 类型 + 可空性 + 顺序的哈希），登记到目标库；
运行期每次（重）连源库都复核一次。于是「有人绕过 binlog 手工改了表结构」也能在写入之前被拦住。

## 不做会出什么事故

| 场景 | 后果 |
|---|---|
| 忽略 DDL | 加列后行镜像列数 > 缓存列数 → 写入错位 → 批次失败 → 增量停摆 |
| 自动执行所有 DDL | 一次 `DROP COLUMN` 就把目标端数据毁掉，且不可回滚 |
| 没有台账 | 事后没人知道「什么时候改了什么」，无法复盘 |
| 没有指纹 | 手工改结构后，错误以「列错位」的形式散落在数据里，极难定位 |

## 自测

1. 为什么 `ADD COLUMN` 可以自动执行，而 `DROP COLUMN` 不行？
2. DDL 台账里存了语句原文，这有什么实际用处？
3. 结构指纹能发现「binlog 之外的变更」吗？为什么？

<details>
<summary>答案</summary>

1. 追加列只增不减，不动既有数据、可重复执行；删除列会让数据永久消失，必须人工确认。
2. 人工在目标库执行时可以直接复制粘贴原文，不用从 binlog 里再挖一遍。
3. 能。它直接读源库的 `information_schema`，不依赖 binlog 里有没有记过这次变更。

</details>

## 速查卡

| 要点 | 一句话 |
|---|---|
| DDL 在哪 | binlog 的 QUERY 事件 |
| 白名单 | 纯追加列，自动执行 |
| 其它 DDL | 记台账 + 任务暂停等人 |
| 台账 | 目标库 `oms_ddl_event`（含语句原文） |
| 指纹 | 建任务登记，运行期复核 |
