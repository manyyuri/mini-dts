# E1 这类系统怎么测：三层，各抓一类毛病

> 「能跑通」和「崩了也对」是两种能力，必须用不同层次的测试分别证明。

## 为什么这节重要

迁移系统的 bug 有个特点：**正常路径几乎不出错，出错全在异常路径**（崩溃、断线、DDL、并发）。
所以测试的重点不是「跑通一次」，而是「故意打断它，看能不能收拾干净」。

![三层测试](../assets/img/fig-e1-tests.png)

## 三层分别抓什么

| 层 | 用什么 | 抓什么毛病 | 局限 |
|---|---|---|---|
| 单测 / 组装测 | H2 两个内存库当源和目标 | 幂等、断点顺序、同事务、编码一致 | 测不到真实 binlog 行为 |
| 崩溃注入 | 在指定位置抛异常，模拟「写了但没记断点」 | 重做后仍一致、不会重复或丢失 | 测不到网络与重连 |
| 端到端 | 两个真 MySQL 容器 + 真 binlog | DDL、断线重连、节点接管、重启恢复 | 慢，靠 Docker 门控 |

## 崩溃注入怎么写

思路：把「写入端口」包一层，在第 N 次提交后抛异常（数据已提交、断点未记），然后重启服务再跑一遍，断言最终两边一致。
这就是第 5 课那个「糟糕但安全」窗口的自动化证明。

## 不做会出什么事故

| 做法 | 事故 |
|---|---|
| 只写「正常跑通」的测试 | 崩溃/断线类 bug 全逃到线上 |
| 只写单测不做端到端 | binlog 相关行为（事件类型、主键变更）全没验证 |
| 端到端必须依赖 Docker 才能跑 | 本地跑不动 → 没人跑 → 形同没有 |
| 测试里 mock 掉「事务边界」 | 恰好把最该验证的东西 mock 掉了 |

## 自测

1. 为什么「幂等」「断点顺序」可以在 H2 上验证？
2. 崩溃注入测试要断言什么？
3. 端到端测试不可替代的那部分是什么？

<details>
<summary>答案</summary>

1. 它们只依赖「SQL 语义 + 事务」，不依赖真实 binlog；H2 的 MySQL 模式足以覆盖。
2. 崩在「已写未记」之后重启，最终两端数据仍一致，且没有重复行。
3. 真实 binlog 事件序列（TABLE_MAP/XID/主键变更）、断线重连、DDL 处置、节点接管。

</details>

## 速查卡

| 层次 | 一句话 |
|---|---|
| H2 双库 | 逻辑正确性，秒级反馈 |
| 崩溃注入 | 「写了没记断点」窗口的证明 |
| Docker E2E | 真实 binlog / 重连 / 接管 |
| 门控 | 无 Docker 自动跳过，不阻塞本地开发 |
